### M0-T1 · Repo scaffold · 2026-11-04
- **Concept:** A reproducible Python project needs a *lockfile* (exact pinned versions + hashes of every transitive dep) and *enforced types*. `uv` gives the lockfile (`uv.lock`); `mypy --strict` turns optional hints into contracts checked at edit-time.
- **Decision:** `uv` for packaging; `ruff` (lint + format) and `mypy --strict` on `app/`; `pytest` + `pytest-asyncio`; `pre-commit` ruff hooks; a root `Makefile` as the single command surface. Installed GNU Make on Windows rather than forking the command vocabulary.
- **Alternatives:** poetry/pip-tools (slower, heavier) vs uv; `just`/`tasks.py` instead of make (but every doc + CI assumes `make`).
- **Tradeoff:** one extra Windows dependency (GNU Make) in exchange for keeping specs, CLAUDE.md §7 and Linux CI all speaking the same commands.
- **Numbers:** `uv sync` resolved 25 packages in ~0.6s, installed 24 in ~3.8s; `make check` (ruff + mypy + 1 test) runs in well under a second.
- **Interview question:** Why do lockfiles matter, and what does strict typing buy you?
- **My answer:** A lockfile pins the exact version and hash of every transitive dependency, so a fresh clone on my laptop, in CI, and in prod all resolve to byte-identical packages — that kills "works on my machine" and makes builds reproducible and auditable. Strict typing (`mypy --strict`) promotes Python's optional hints into enforced contracts, so `None`-handling mistakes, wrong signatures, and refactor breakage are caught at edit-time instead of in production. The cost is a bit more upfront annotation, but the payoff compounds as the codebase and team grow. It also documents intent: the types are a spec that can't drift from the code.

### M0-T2 · Settings, logging, errors · 2026-11-04
- **Concept:** The request-handling backbone: 12-factor config (one typed `Settings` from env), structured JSON logs correlated by a `request_id` carried in a `contextvar`, and a domain-error hierarchy mapped to one stable JSON shape at the HTTP edge.
- **Decision:** `pydantic-settings` for config; `structlog` → JSON with a `request_id` processor; a `ContextVar` + HTTP middleware to carry the id; `AppError` subclasses (each with a stable `code` + `status_code`) mapped by one exception handler to `{error:{code,message,request_id}}`.
- **Alternatives:** scattered `os.getenv` (untyped); stdlib `logging`/`loguru` (weaker processor model); raising `HTTPException` inside services (couples business logic to FastAPI, breaks layering).
- **Tradeoff:** a bit of setup ceremony (processor chain, middleware, error classes) and one central config module everything imports — accepted because it buys type-safety, log correlation, and transport-free services.
- **Numbers:** 11 unit tests, `make check` ~3s; log lines are single-line JSON with `request_id`, `level`, `timestamp`.
- **Interview question:** Why route domain errors through one handler instead of raising `HTTPException` in your services, and why a stable `code` field?
- **My answer:** Services live below the API layer and must stay transport-agnostic, so they raise domain errors (`NotFoundError`, `BudgetExceededError`) that carry a stable machine-readable `code` and an HTTP status, but know nothing about FastAPI. A single exception handler at the edge translates any `AppError` into one consistent JSON envelope, `{error:{code,message,request_id}}`, which means clients branch on `code` — a contract that never changes — rather than on human-readable messages that get reworded. The `request_id` in both the body and the `X-Request-ID` header ties a user's error report straight to the correlated log lines. It also centralizes the guarantee that we never leak internals or stack traces to clients.

### M0-T3 · Local infrastructure · 2026-11-04
- **Concept:** Run the stateful backing services (Postgres, Redis, Qdrant) as containers via Docker Compose so local = CI = prod, with health checks that report *readiness* (accepting queries), not just liveness (process started).
- **Decision:** `docker-compose.yml` with pinned images (`postgres:16`, `redis:7`, `qdrant/qdrant:v1.12.4`), per-service healthchecks, named volumes (`pgdata`, `qdrant_data`); `make up` = `docker compose up -d --wait` (blocks until healthy, idempotent). Postgres init script creates `app_test` for integration tests.
- **Alternatives:** native installs on Windows (version drift, hard to reset); one shared DB for tests and dev (risk of tests clobbering dev data).
- **Tradeoff:** Docker Desktop must be running; bind mounts/ports need Windows care — accepted for reproducibility and one-command setup.
- **Numbers:** cold `make up` ≈ image pull time; warm start to all-healthy ≈ a few seconds; three containers.
- **Interview question:** What's the difference between a liveness and a readiness check, and why does it matter in a compose/orchestrated setup?
- **My answer:** Liveness answers "is the process alive?" — restart it if not. Readiness answers "can it actually serve requests right now?" — e.g. Postgres has finished recovery and is accepting connections. They differ during startup and transient overload: a container can be *live* but not yet *ready*. In Compose I use `--wait` on healthchecks so dependents (migrations, tests, the API's `/readyz`) only proceed once services are truly ready, which avoids flaky "connection refused" races. In Kubernetes the same split drives traffic routing (readiness gates the Service) versus restarts (liveness), so conflating them can either drop traffic or crash-loop a pod that just needed a moment.

### M0-T4 · Database layer · 2026-11-14
- **Concept:** Async SQLAlchemy 2.0 over asyncpg so DB I/O yields the event loop; a pooled engine; Alembic for versioned migrations; the repository pattern to keep SQL out of services; UUIDv7 primary keys and UTC `timestamptz` audit columns.
- **Decision:** cached async engine + `async_sessionmaker` + a `get_session` dependency; `UUIDAuditBase` (uuid7 id, created/updated); `User` model; `UserRepository` (flush, not commit — caller owns the transaction); async Alembic `env.py` pulling URL+metadata from the app; unit/integration split via a pytest marker so `make check` needs no DB.
- **Alternatives:** sync SQLAlchemy/psycopg (blocks the loop); ORM calls directly in services (couples logic to persistence, hard to unit-test); auto-increment int PKs (not globally unique, leaks row counts); `gen_random_uuid()` server default (that's UUIDv4 — not time-ordered).
- **Tradeoff:** async adds a `greenlet` bridge and more moving parts; repositories are a little boilerplate — accepted for non-blocking I/O and testable, swappable data access.
- **Numbers:** pool_size 5 + max_overflow 10 (configurable); 1 integration test create→read; `make migrate` created `users` + `alembic_version`.
- **Interview question:** What happens if your DB connection pool is too small? Too large? And why UUIDv7 over a plain UUID or an auto-increment id?
- **My answer:** Too small and requests serialize waiting for a free connection — latency climbs and you get pool-timeout errors under load even though Postgres is idle. Too large and every app replica multiplies its pool against Postgres's hard `max_connections`, so you exhaust server slots, burn memory, and can crash the database; the fix at scale is a pooler like PgBouncer rather than ever-bigger app pools. UUIDv7 is time-ordered, so new rows insert near the right edge of the B-tree index (good locality, less page fragmentation) while staying globally unique and non-guessable — unlike auto-increment ints, which leak counts and collide across shards, and unlike UUIDv4, whose randomness scatters writes across the index.

### M0-T5 · FastAPI app · 2026-11-14
- **Concept:** An app factory that composes the pieces built so far — request-id middleware, domain-error handlers, CORS — and exposes operational endpoints: `/healthz` (liveness), `/readyz` (readiness: Postgres + Redis + Qdrant, 503 if any down), `/metrics` (Prometheus request histograms). A dev-auth dependency returns a fixed local user so the app is usable without login.
- **Decision:** `create_app()` factory + module-level `app` for `uvicorn app.main:app`; readiness runs the three checks concurrently with `asyncio.gather`, each bounded by a 3s timeout; `prometheus-fastapi-instrumentator` for `/metrics`; `Principal` from a dev-auth dependency (real OAuth in M7).
- **Alternatives:** a global app built at import with no factory (harder to test/configure per-env); readiness that only checks the process (misses dependency outages); checking deps sequentially (slower, unbounded).
- **Tradeoff:** the factory + instrumentation add a little wiring; bounded checks can report a slow-but-alive dependency as not-ready — accepted, because a readiness probe must be fast and must never hang.
- **Numbers:** readiness fan-out bounded at 3s/check; live boot verified `/docs` 200 and `/readyz` all-true; 4 new unit tests + 1 readiness integration test.
- **Interview question:** Why separate `/healthz` from `/readyz`, and what exactly does each check?
- **My answer:** `/healthz` is liveness — it only proves the process is running and the event loop responds; an orchestrator uses it to decide whether to restart the container. `/readyz` is readiness — it actively checks that every backing service (Postgres, Redis, Qdrant) answers, and returns 503 if any is down, so the load balancer stops sending user traffic to an instance that would just error. Conflating them is dangerous: if liveness also checked the database, a brief DB blip would make Kubernetes kill and restart healthy app pods (a crash-loop) instead of simply pausing traffic. I run the readiness checks concurrently with per-check timeouts, because a probe that hangs is worse than one that fails — a stuck probe ties up the orchestrator and hides the real state.

### M0-T6 · LLM gateway v0 · 2026-11-14
- **Concept:** A single gateway for every LLM call so retries, timeouts, fallbacks, cost and tracing live in one place. Transient failures are retried with exponential backoff + full jitter; an exhausted model falls back to the next in the alias's chain; structured calls validate JSON against a Pydantic schema.
- **Decision:** alias→(models, timeout) resolution from config; `retry_with_backoff` (attempts, base, cap, jitter) wrapping each model; fallback loop across the chain; `complete`/`structured`/`stream`; cost+latency computed and logged. Tested against a mocked LiteLLM (no keys). Langfuse + `llm_calls` persistence deferred to M1.
- **Alternatives:** provider SDKs called directly in services (no central retries/budgets/traces); fixed-interval retries (thundering herd); retrying with no cap (unbounded latency); free-text LLM output (unparseable, unevaluable).
- **Tradeoff:** an extra layer every call passes through, and retries add latency on failures — accepted for reliability, swappable providers, and one place to enforce cost/tracing.
- **Numbers:** attempts = max_retries + 1 (default 3); backoff base 0.5s capped at 8s; full jitter; mocked-LiteLLM tests cover fallback, 429-retry-then-succeed, cost recording, schema validation.
- **Interview question:** What's the relationship between retries and idempotency, and why add jitter?
- **My answer:** Retrying is only safe when the operation is idempotent — if a call might have succeeded before the error (e.g. a timeout on the response, not the request), a blind retry can double the effect, so write operations need idempotency keys while pure reads like an LLM completion are naturally safe to repeat. Exponential backoff spaces out retries so a struggling provider gets time to recover instead of being hammered. Jitter adds randomness to each delay so that many clients that all failed during the same outage don't retry in lockstep the instant it recovers — without it you get a synchronized "thundering herd" that spikes load and causes a second outage. Full jitter (uniform between 0 and the capped delay) is the simple, well-tested choice.

### M0-T7 · Prompt registry · 2026-11-14
- **Concept:** Treat prompts as versioned artifacts, not strings in code. Files live at `app/prompts/<name>/v<N>.md` with YAML front matter (model alias, temperature, description) and a Jinja2 body; code references them by (name, version). A change means a NEW version file, so a prompt change is a reviewable diff and an eval can pin a version.
- **Decision:** a small registry (`load_prompt`/`render_prompt`, cached) using Jinja2 with `StrictUndefined` so a missing variable raises; a `prompts-sync` command that validates every prompt compiles (CI-useful) and defers the Langfuse push to M1.
- **Alternatives:** f-strings/constants in code (no diff history, no versioning, no eval pinning); editing a prompt in place (silently changes behaviour for every past eval/trace).
- **Tradeoff:** a tiny bit of loader machinery and the discipline of adding version files — worth it for reviewable, rollback-able, independently-evaluable prompts.
- **Numbers:** 6 registry tests; `StrictUndefined` turns a missing template variable into a loud error instead of an empty string.
- **Interview question:** Why version prompts in files instead of editing them in place, and why is a prompt change effectively a deploy?
- **My answer:** A prompt is as load-bearing as code — it determines model behaviour — so it deserves the same discipline: a new version is a new file, which gives a reviewable diff, a clean rollback, and a stable identifier an eval run or a trace can pin to. If I edited a prompt in place, every historical eval score and Langfuse trace would silently refer to text that no longer exists, so I could never reproduce or compare results. That's why a prompt change is a deploy: it can change faithfulness, latency, and cost, so it must pass the same eval gate and be rolled out (and rolled back) like any code change.

### M0-T8 · CI · 2026-11-14
- **Concept:** Continuous integration runs the same gates on every push/PR that we run locally, so regressions are caught before merge. Two jobs: a fast `unit` job (ruff + mypy + unit tests) and an `integration` job that spins up Postgres/Redis/Qdrant as service containers.
- **Decision:** GitHub Actions `ci.yml`; `uv sync` for reproducible installs (the lockfile is the truth); the CI runs `make check` and `make test-int`, so local and CI share one command surface; service containers get health checks so steps wait for readiness.
- **Alternatives:** running tests only locally (relies on memory/discipline); baking a custom Docker image with the services (slower than ephemeral service containers for this size).
- **Tradeoff:** CI minutes and a bit of YAML to maintain — free on a public repo, and cheap insurance against "works on my machine".
- **Interview question:** Why run integration tests with service containers in CI instead of mocking the database?
- **My answer:** Mocks verify my code against my *assumptions* about Postgres/Redis/Qdrant; service containers verify it against the *real* engines — so I catch SQL dialect issues, migration errors, driver quirks and readiness races that a mock would hide. I keep the fast unit job (mocked adapters) as the first gate for quick feedback, and run the slower integration job against ephemeral real services for fidelity. Ephemeral containers also give each run a clean, identical starting state, which keeps the tests deterministic.

### M1-T2 · Ingestion pipeline · 2026-11-14
- **Concept:** Turn `content/` into retrievable chunks. Load note → strip front matter → heading-aware chunk (LlamaIndex `MarkdownNodeParser` → `SentenceSplitter`, 512/64) → attach metadata (title, section path, topic_ids, licence, kb_version) → persist `documents` + `chunks`. A per-document content hash skips unchanged docs; a changed doc's chunks are replaced atomically (delete old + insert new in one transaction).
- **Decision:** LlamaIndex for parse/chunk (own the retrieval/rerank/citation parts later); `source_key` as the stable identity (notes' relative path) for skip/replace; chunks store `topic_ids` + `kb_version`; vector/Qdrant upsert is a separate seam added in M1-T3.
- **Alternatives:** fixed-size character chunking (ignores structure, splits mid-idea); re-ingesting everything each run (wasteful, and risks serving half-updated content); dropping+recreating all chunks globally (a reader could see an empty KB mid-rebuild).
- **Tradeoff:** heading-aware chunking + hashing is more logic than naive splitting, but it gives better retrieval granularity and cheap incremental re-ingest.
- **Numbers:** 8 notes → 63 chunks; chunk target 512 tokens / 64 overlap; re-running ingest on unchanged content does zero writes (8 skipped).
- **Interview question:** How do you re-ingest changed content without serving a half-updated document, and how do you avoid redoing work?
- **My answer:** Each document has a content hash; on ingest I compare it and skip the document entirely if unchanged, so re-running is nearly free and only touched files do work. For a changed document I replace its chunks atomically — delete the old chunks and insert the new ones inside a single transaction — so a concurrent reader either sees the complete old version or the complete new one, never a mix or an empty gap. The stable `source_key` means the same file maps to the same document row across runs, so I update in place rather than duplicating. At scale the same idea extends to the vector store with a write-new-then-switch-then-delete-old swap so Qdrant is never partially updated either.

### M1-T3 · Embeddings and Qdrant · 2026-11-16
- **Concept:** Make chunks searchable. fastembed (CPU, ONNX) produces a 384-d dense vector (bge-small) and a BM25 sparse vector per chunk; Qdrant stores both as named vectors on one point (`kb_chunks`), compared with cosine (dense) and BM25-with-IDF (sparse). Dense catches paraphrase/meaning; sparse catches exact technical tokens.
- **Decision:** our own `VectorStore` adapter (Protocol) over qdrant-client + fastembed, not LlamaIndex's wrapper, so M1-T4/T5 get direct access to the two ranked lists for our own RRF + reranking; the chunk's DB id is the Qdrant point id; payload indexes on `topic_ids`/`kb_version`/`document_id`; upsert wired into ingestion (delete-then-upsert per changed doc). Pinned qdrant-client to the server's 1.12 line to kill a version-drift warning.
- **Alternatives:** dense-only (misses exact terms like `HNSW`); pgvector (no native hybrid/sparse, less control); a paid embedding API (cost + rate limits vs free local CPU).
- **Tradeoff:** running embeddings on CPU is slower than a GPU/API, but it's free, has no rate limits, and keeps data local — fine at our corpus size.
- **Numbers:** 384-dim dense; 8 docs → 63 chunks → 63 Qdrant points; integration test finds the right chunk by a word-disjoint paraphrase (dense) and by the exact term "BM25" (sparse).
- **Interview question:** Why store both a dense and a sparse vector, and what do HNSW's `m` and `ef` control?
- **My answer:** Dense embeddings match meaning, so a paraphrase with no shared words still retrieves the right chunk, but they can blur rare exact tokens like `QLoRA` or `HNSW`; BM25 sparse vectors score exact term overlap with IDF weighting and nail those, so keeping both and fusing them (RRF, next ticket) beats either alone. HNSW is the approximate-nearest-neighbour graph Qdrant searches: `m` is the number of links per node (bigger graph → better recall but more memory), `ef_construct` is how many candidates are considered while building the graph (build-time quality), and `ef` is the search-time beam width (bigger → higher recall but slower queries). They're the knobs on the recall-vs-latency/memory tradeoff.

### M1-T4 · Hybrid retrieval and fusion · 2026-11-16
- **Concept:** Query dense and sparse separately, then merge the two ranked lists with Reciprocal Rank Fusion: an item's score is Σ 1/(k+rank) over the lists it appears in (k=60). Using rank, not raw score, makes fusion scale-free — essential because cosine and BM25 scores aren't comparable.
- **Decision:** our own `reciprocal_rank_fusion` + a `HybridRetriever` that fuses `search_dense` + `search_sparse` and applies a `topic_ids` payload filter at the Qdrant level; also exposed Qdrant's native RRF (`search_hybrid_native`) for comparison.
- **Alternatives:** averaging/adding the two scores (meaningless across scales, dominated by whichever scorer has the larger range); min-max normalising then adding (fragile, sensitive to outliers); dense-only (loses exact-term recall).
- **Tradeoff:** RRF discards score magnitude (how *confident* a ranker was), keeping only order — simple and robust, and a reranker (M1-T5) restores fine-grained ordering on the top-N.
- **Numbers:** k=60 (standard); fuse to top-30; 5 RRF unit tests (ties, missing ids, k effect); larger k provably flattens rank gaps.
- **Interview question:** Why reciprocal rank fusion instead of averaging the dense and sparse scores?
- **My answer:** Cosine similarity and BM25 produce scores on completely different, uncalibrated scales, so adding or averaging them lets whichever scorer has the larger numeric range dominate — the result is noise, not a principled combination. RRF throws the magnitudes away and uses only each document's rank in each list: score = Σ 1/(k + rank), so a document that ranks highly in either retriever floats to the top, and one that ranks well in both wins. It's parameter-light (just k, which smooths how much top ranks dominate), needs no per-corpus tuning, and is robust to outlier scores. The cost is losing the confidence signal in the magnitudes, which is why I rerank the fused top-N with a cross-encoder afterwards.

### M1-T5 · Reranker · 2026-11-16
- **Concept:** A cross-encoder reads (query, chunk) together with full cross-attention and emits one relevance score — much more accurate than the bi-encoder, but it can't be precomputed, so run it only on the fused top-N (30 → 6). Restores the fine-grained ordering RRF discards.
- **Decision:** fastembed `TextCrossEncoder` (MiniLM MS-MARCO) behind a `Reranker`; config switch `RERANK_ENABLED` to bypass it; latency logged per call; replaces each chunk's fused score with the cross-encoder score.
- **Alternatives:** no rerank (ship fused order — weaker precision@k); rerank the whole corpus (quadratic cost, infeasible); an LLM reranker (far slower/pricier than a 22M-param cross-encoder on CPU).
- **Tradeoff:** adds ~CPU latency on the top-N, but only on a small N, for a big precision gain — and it's toggleable for the eval comparison in M1-T6.
- **Numbers:** rerank 30 → 6; MiniLM-L-6 cross-encoder (~22M params, CPU/ONNX); latency logged for the 30-pair batch.
- **Interview question:** Bi-encoder vs cross-encoder — why use both, and why rerank only the top-N?
- **My answer:** A bi-encoder embeds the query and each document independently, so document vectors are precomputed and indexed and I can search millions in milliseconds — but independence means it never sees the query and document together, so its scoring is coarse. A cross-encoder feeds the pair through the model jointly with full attention, which is much more accurate but can't be precomputed, so scoring the whole corpus would be O(corpus) forward passes — infeasible. The standard pattern is retrieve-then-rerank: the cheap bi-encoder (plus BM25) gets a high-recall top-30, then the expensive cross-encoder reorders just those 30 into a high-precision top-6. I rerank only the top-N because cost scales with N, and beyond the first few dozen candidates the recall gain isn't worth the latency.

### M1-T6 · RAG golden set and retrieval evals · 2026-11-17
- **Concept:** You can't tune retrieval you can't measure. A golden set maps questions → expected documents; recall@k asks "is the right doc in the top-k?" and MRR rewards ranking it higher. Compare dense / sparse / hybrid / hybrid+rerank on the same set so changes are evidence-based.
- **Decision:** `evals/datasets/rag_golden.jsonl` keyed by note `source_key` (I added `source_key` to the Qdrant payload + `RetrievedChunk` for stable identity); a runner computing recall@5/10 + MRR across the four configs, writing a markdown table to `evals/reports/`; `make eval-retrieval`.
- **Alternatives:** eyeballing a few queries (not reproducible, no regression signal); tuning chunk size/top-k before having a golden set (optimising blind).
- **Tradeoff:** building the golden set is manual effort, but it's the only way to make retrieval changes measurable and gate regressions in CI later.
- **Numbers:** seed set 15 answerable + 3 unanswerable; on this small, well-separated corpus all configs score recall@5 = 1.000 (sparse MRR 0.967) — the harness is validated, but the set must grow to 80 (and notes need prose) before the numbers discriminate between configs.
- **Interview question:** Why build the golden set before tuning retrieval, and what do recall@k and MRR each tell you?
- **My answer:** Without a fixed golden set, any tuning is guesswork — I can't tell whether a chunk-size or fusion change actually helped or just shifted a couple of anecdotal queries, and I have no way to catch a regression later. Recall@k answers "did we fetch the right document at all within the top-k?", which is what matters because the reranker and generator can only work with what retrieval surfaces; MRR adds "how high did we rank it?", rewarding putting the answer at position 1 over position 5. I report both, plus abstention precision/recall on the unanswerable questions, and I compare dense/sparse/hybrid/+rerank on the identical set so every change is a controlled experiment. My seed numbers are near-perfect only because 15 questions over 8 distinct notes is easy — the honest move is to grow the set until it actually separates the configurations.

### M1-T7 · Answer generation, citations, abstention · 2026-11-18
- **Concept:** Turn retrieved chunks into a grounded, cited answer. Numbered sources go into a delimited block the prompt treats strictly as *data, not instructions* (prompt-injection defense); the model must cite each claim [n]; `verify_citations` strips any [n] outside the source range; if the top rerank score is below a threshold the assistant abstains instead of inventing.
- **Decision:** 3 style prompts (`study_answer/{concise,interview,deep}`); `StudyService` orchestrates retrieve → rerank → abstain-or-generate → verify, yielding SSE events; generate via non-streaming `complete` so citations verify before sending; gateway bridges `GEMINI_API_KEY` into `os.environ` for LiteLLM.
- **Alternatives:** stream raw tokens then verify (can't strip a bad citation already sent); no abstention (confident hallucination on out-of-KB questions); trusting the model's citations unchecked (hallucinated [n]).
- **Tradeoff:** verifying before sending costs true incremental streaming for now; accepted — correctness of citations matters more than token-by-token feel at this stage.
- **Numbers / live finding:** 43 unit tests (mocked gateway) green; live Gemini call confirmed the key authenticates and the pipeline is wired, but surfaced two real ops lessons — model ids rotate (`gemini-2.0-flash` → 404 "retired", API pointed to `gemini-3.8-flash`), and the free tier throttles (503 "high demand" / read timeouts), which is exactly why the gateway owns timeouts, retries and a fallback chain.
- **Interview question:** How do you stop a RAG system from hallucinating, and what happens when the knowledge base doesn't cover the question?
- **My answer:** Three layers. First, grounding: the prompt forbids outside knowledge and requires a [n] citation for every claim, with the sources in a delimited block treated as data so injected instructions in a document can't hijack the model. Second, verification: after generation I check every [n] maps to an actually-retrieved source and strip the ones that don't, tracking a citation-invalid rate. Third, abstention: if the best reranked chunk scores below a tuned threshold, the assistant says "not covered yet" and suggests the nearest topics instead of answering — and I log it as a content gap so I know what to add to the KB. The threshold trades off abstain precision vs recall, which I tune on the golden set's answerable + unanswerable split.

### M1-T8 · Conversation memory and query rewriting · 2026-11-18
- **Concept:** Follow-ups like "what about memory?" are meaningless to a retriever on their own. We keep `conversations`/`messages`, load the last 6 turns, and use the fast model to rewrite the follow-up into a standalone query (skipped on the first turn), then retrieve/answer with that.
- **Decision:** `ConversationRepository`; `StudyService` gains an optional `conversation_id` (no id → one-off ask, unchanged) and its own short-lived sessions (not request-scoped, so SSE streaming can't close the session mid-stream); the rewritten query is used for retrieve/rerank/generate; both messages persisted. `UserRepository.ensure` seeds the dev user so the conversation FK holds.
- **Alternatives:** stuffing all prior turns into the answer prompt (blows the context window, retrieves on noise); no rewrite (the follow-up retrieves garbage); holding one request session across the whole SSE stream (session closes before streaming finishes).
- **Tradeoff:** an extra fast-model call per follow-up (latency + cost) to make retrieval coherent — worth it; and the rewrite can occasionally over/under-specify, which evals will catch.
- **Numbers:** last 6 turns as context; one extra `fast` call per follow-up; AC test persists 4 messages and confirms the LoRA chunk is retrieved from a bare "what about memory?".
- **Interview question:** How does your assistant handle a follow-up like "and how does that affect memory?", and why rewrite instead of just appending history?
- **My answer:** Retrieval is only as good as the query, and a bare follow-up has no subject — embedding "what about memory?" retrieves noise. So before retrieving I take the last few turns and have a cheap fast model rewrite the follow-up into a self-contained query like "how does LoRA affect memory usage?", then retrieve and answer on that. I rewrite rather than dumping the whole history into the retrieval query because history is long and mostly irrelevant tokens that dilute the embedding and hurt recall; a focused standalone query is what the dense and sparse retrievers actually want. I skip the rewrite on the first turn (nothing to resolve) and I keep the user's original wording in the stored transcript. The one cost is an extra LLM call per follow-up, which is why it uses the fast alias.

### M1-T9 · Ragas evaluation · 2026-11-18
- **Concept:** Measure answer quality, not just retrieval. Ragas scores each (question, answer, contexts, reference) on faithfulness (is every claim entailed by the contexts?), response relevancy (does the answer address the question?), context precision (are retrieved contexts relevant?) and context recall (do they cover the reference?). The judge LLM is Groq; embeddings are our local fastembed (Groq has no embeddings API).
- **Decision:** `evals/ragas_run.py` runs our pipeline per golden question then scores with Ragas; eval-only deps live in an `evals` uv group; `make eval-fast` (subset) / `make eval-full` (all). `ResponseRelevancy(strictness=1)` because Groq rejects the OpenAI `n>1` multi-sample param.
- **Alternatives:** judging faithfulness by hand (not scalable/repeatable); retrieval metrics alone (say nothing about whether the generated answer is grounded).
- **Tradeoff:** Ragas fires many judge calls (rate-limited on the free tier, so it's slow) and the scores are themselves LLM estimates — directional, to be trended, not absolute truth.
- **Numbers (baseline, 15 answerable):** faithfulness 0.66, answer_relevancy 0.80, context_precision 0.83, context_recall 0.87. Faithfulness is below the 0.90 target because the KB notes are still outlines — a baseline to improve with prose + tuning, not a pass/fail yet.
- **Interview question:** What does Ragas faithfulness measure, and what does a low score tell you?
- **My answer:** Faithfulness is the share of claims in the answer that are actually supported by the retrieved contexts — it's the direct, automatic signal for hallucination in RAG. A low faithfulness with *high* context recall (my case: 0.66 vs 0.87) is diagnostic: retrieval is finding the right material, so the problem is generation drifting beyond the sources — thin source text, or the model embellishing. The fixes are on the generation side: richer grounding content, a stricter "cite every claim / don't go beyond the sources" prompt, and citation verification — not more retrieval tuning. I treat the number as directional (the judge is itself an LLM) and trend it across prompt/model changes rather than reading one run as ground truth.

### M2-T1 · Rubrics and question bank · 2026-11-18
- **Concept:** A store of questions (MCQ / short / flashcard) tagged by `topic_ids` + difficulty, plus rubrics (scoring dimensions) for grading short answers. Questions are also embedded into a Qdrant `questions` collection so M2-T2 can detect near-duplicates before approving generated ones.
- **Decision:** `rubrics` + `questions` tables (GIN index on `topic_ids`, composite index on `(status, kind)`); a Pydantic-validated YAML bank with idempotent import keyed by a per-question `ext_key` (explicit slug or a text hash); import writes Postgres rows and upserts question vectors.
- **Alternatives:** questions as code/constants (no review workflow, no status lifecycle); no stable import key (re-import duplicates); a separate ids file (drift).
- **Tradeoff:** a bit of import machinery + a second Qdrant collection, for a reviewable, de-dupable, taxonomy-tagged bank that quizzes and the generator build on.
- **Numbers:** seed = 1 rubric + 12 questions across LLM/retrieval/RAG/FT/eval; idempotent re-import (verified: counts stable in Postgres and Qdrant).
- **Interview question:** How do you keep an LLM-generated question bank trustworthy and free of duplicates?
- **My answer:** Every question has a status lifecycle (draft → approved → retired) so generated ones never reach quizzes until reviewed, and a validator pipeline (M2-T2) checks each is answerable from its cited source, has exactly one correct option, and isn't a near-duplicate. Duplicate detection is semantic, not exact: I embed each question and query the Qdrant questions collection, rejecting anything above a cosine threshold (~0.92) against existing questions. Exact import idempotency is separate — a stable `ext_key` (slug or text hash) means re-importing the YAML updates rather than duplicates. Tagging by `topic_ids` is what lets the daily drill target weak topics and the planner map a job post to the right questions.

### M2-T2 · Question generator with validation · 2026-11-18
- **Concept:** Generate MCQs from KB chunks, then *gate* each one rather than trusting the model. Validators: valid JSON (structured output schema), structural (4 options, exactly one correct, distinct, non-empty), answerable-from-source (a second LLM check), and near-duplicate (cosine ≥ 0.92 vs the questions index). Survivors land as `draft` for admin approval.
- **Decision:** `QuestionGenerator` using `gateway.structured` for schema-enforced output; deterministic structural checks + an LLM answerability check + semantic dedup; admin endpoints (list draft / approve / retire / generate). Generated via Groq.
- **Alternatives:** "generate and hope" (ships wrong/ambiguous/duplicate questions); exact-text dedup only (misses paraphrased duplicates); no review lifecycle (bad questions reach users).
- **Tradeoff:** more LLM calls per accepted question (generate + verify) and some good questions rejected by a conservative dedup threshold — accepted, because question quality is a product-trust issue.
- **Numbers:** live run on `ft.lora_qlora` generated 3 → accepted 1, rejected 2 as duplicates; each accepted question costs a generate (strong) + an answerability check (fast) call, $0 on Groq.
- **Interview question:** How do you make sure LLM-generated quiz questions are correct, and why a validator pipeline?
- **My answer:** I never let the model's output go straight to users — it goes through a validator pipeline and a draft→approved lifecycle. First the output is schema-constrained (structured JSON), then deterministic checks enforce exactly one correct option with distinct, non-empty distractors; then a separate LLM call verifies the question is actually answerable from the cited source and the key is right (catching confidently wrong keys); then semantic dedup rejects near-duplicates by embedding similarity, not exact text, so paraphrases don't slip through. Only survivors become `draft`, and a human approves before they appear in a quiz. The pipeline beats "generate and hope" because each failure mode — hallucinated answer, ambiguous distractors, duplicates — has a specific gate, and I can measure a validity rate on a human-reviewed sample to tune thresholds.

### M2-T3 · Grading · 2026-11-18
- **Concept:** Grade each question kind the right way: MCQ by exact match (deterministic), flashcards by the user's self-rating, and short answers by the fast model against the question's rubric + reference (structured score 0-1 + feedback).
- **Decision:** a `GradingService` returning `GradeResult(correct, score, explanation)`; MCQ accepts either the option index or the option text; short-answer grading uses a rubric-aware prompt and clamps the score to [0,1]; a short answer counts as correct at ≥0.6. Flashcard ratings map again/hard/good/easy → 0/0.4/0.8/1.0.
- **Alternatives:** LLM-grading everything (wasteful and non-deterministic for MCQ); keyword matching for short answers (misses paraphrases and partial credit).
- **Tradeoff:** short-answer grading is an LLM estimate, so it needs calibration against human grades — which is exactly the M2-T3 acceptance eval (agreement on 40 answers).
- **Numbers:** 6 unit tests; short-answer pass threshold 0.6; the short grader is a single fast-model structured call per answer.
- **Interview question:** How do you grade short answers fairly, and how do you know the grader is any good?
- **My answer:** I grade short answers with the fast model against the question's reference answer and a rubric (weighted dimensions like correctness/completeness/clarity), returning a 0-1 score plus one-line feedback, and I treat ≥0.6 as a pass. Because the grader is itself an LLM, I don't trust it blind — I calibrate it the same way as the interview judge: collect human grades on a sample (40 answers here), and measure agreement with quadratic-weighted kappa, looking at every 2+ point disagreement to tighten the rubric or prompt. MCQ and flashcards don't need the LLM at all — exact match and self-rating are deterministic — so I only spend a model call where judgement is actually required.

### M2-T4 · Skill model · 2026-11-18
- **Concept:** Track mastery per (user, topic) with an Elo/IRT-style update: mastery lives in [0,1] but updates on the logit scale against the question's difficulty, so `expected = σ(mastery_logit − difficulty_logit)` and `mastery_logit += K·(outcome − expected)`. Confidence grows with attempts and decays with time since the last evidence.
- **Decision:** `skill_states` (composite PK (user, topic)) + `skill_events` (audit trail of every delta); a pure `update_mastery` function (testable without a DB) + a `SkillsService` that persists state and an event per answer; difficulty 1-5 mapped to logits −2..+2.
- **Alternatives:** averaging past scores (ignores difficulty — a win on an easy question counts the same as a hard one); fixed ± increments (no notion of surprise); no confidence/recency (can't tell a well-tested topic from a lucky one, or a stale one).
- **Tradeoff:** a logit model is less transparent than a running average, but it correctly rewards hard wins and punishes easy losses, which is what adaptive drills need.
- **Numbers:** K=0.3; confidence half-life 30 days; tests confirm correct-on-hard > correct-on-easy and wrong-on-easy < wrong-on-hard.
- **Interview question:** How does your skill model treat a hard question versus an easy one?
- **My answer:** It uses an Elo/item-response idea: the update is proportional to how *surprising* the outcome was. Expected success is σ(mastery − difficulty), so against a hard question expected success is low — getting it right is surprising and pushes mastery up a lot, while getting it wrong was expected and barely moves it. Against an easy question it's the reverse: a correct answer was expected so it adds little, but a wrong answer is surprising and drops mastery sharply. That's the behaviour a plain average can't capture, because an average weights every question equally regardless of difficulty. I also track a separate confidence that rises with the number of attempts and decays over time, so the scheduler can tell a genuinely-mastered topic from one with thin or stale evidence.

### M2-T5 · Spaced repetition (FSRS) · 2026-11-18
- **Concept:** Schedule each card's next review using FSRS, which models the forgetting curve per card (a stability and difficulty that evolve with each review) and picks the interval that lands near a target recall probability. Again/Hard/Good/Easy ratings move the schedule; a lapse shrinks the interval, a success grows it.
- **Decision:** `review_cards` (PK (user, question), FSRS state as JSONB + `due_at` + `last_review_at`, index on (user, due_at)); a pure `schedule()` wrapping the `fsrs` package (testable) + `SchedulerService` that persists; graded outcomes map correct→Good, wrong→Again, flashcards pass the self-rating straight through.
- **Alternatives:** fixed doubling intervals (ignore how hard a card is for *this* user); Leitner boxes (coarse); reviewing everything daily (wastes time on known cards).
- **Tradeoff:** FSRS is a heavier model (per-card state, a trained parameter set) than fixed intervals, but it schedules far more efficiently — fewer reviews for the same retention.
- **Numbers:** ratings Again/Hard/Good/Easy; new-card intervals order again < good ≤ easy; a second Good pushes the due date further out (verified in tests).
- **Interview question:** Why spaced repetition instead of random or fixed-interval review?
- **My answer:** The forgetting curve says recall decays exponentially and each successful review flattens that curve, so the optimal time to review is just as you're about to forget — too early wastes effort, too late means you've already lost it. Fixed intervals ignore that a card can be easy for one person and hard for another; FSRS fits a per-card stability and difficulty from your actual review history and schedules each card to hit a target recall (say 90%), which gets the same retention for far fewer reviews. I map a correct quiz answer to a Good rating and a wrong one to Again (which collapses the interval so you see it again soon), and flashcards pass their self-rating straight through. Combined with the skill map, overdue-and-weak topics are exactly what the daily drill pulls first.

### M2-T6 · Daily drill builder + quiz API · 2026-11-18
- **Concept:** Assemble a 10-minute drill and run the answer loop. Selection: exclude questions seen in the last 14 days, put due-for-review cards first, then weakest topics (lowest mastery), cap any single kind to keep variety, and make it deterministic with a seed. Answering grades the response, updates the skill map, and reschedules the card — one transaction.
- **Decision:** a pure `select_drill` (seeded, unit-tested per rule) + a `QuizService` wiring `GradingService`, `SkillsService`, and `SchedulerService`; `quiz_sessions`/`quiz_answers` tables; endpoints `GET /today`, `POST /answer`, `POST /sessions/{id}/finish`. The drill never leaks answers to the client.
- **Alternatives:** random selection (reviews things you already know, ignores forgetting); grading without updating skills/schedule (the map and SRS go stale); non-deterministic selection (impossible to test).
- **Tradeoff:** the selection has several interacting rules — kept pure and seeded so each is independently testable — and answering fans out to three services, which is more coupling but is the whole point of one shared skill map.
- **Numbers:** drill size 10, per-kind cap ~60%, 14-day no-repeat window; 5 selection unit tests + a full today→answer→finish integration test.
- **Interview question:** How does your daily drill decide what to show, and why is it built as a pure, seeded function?
- **My answer:** It prioritises by spaced-repetition need then by weakness: anything due for review (FSRS) comes first, then the lowest-mastery topics, after dropping anything answered in the last two weeks so you're not re-shown fresh items, with a per-kind cap so a drill isn't all MCQs. The core selection is a pure function of (candidates, due-set, mastery-by-topic, seen-set, size, seed), which matters because selection logic is exactly the kind of thing that silently regresses — making it pure and seeded lets me unit-test each rule in isolation and reproduce any drill. The side-effecting part (grade → update mastery → reschedule) lives in the service layer and runs in one transaction, so a graded answer always moves the skill map and the review schedule together.
